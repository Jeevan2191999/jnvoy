Privacy and data handling

What happens to your text when it passes through Jnvoy, what we keep, who else sees it, and where redaction can fall short.

The short version

Jnvoy replaces sensitive values in your prompts with placeholder tokens before the prompt reaches a language model, then puts the real values back into the reply.

How a request flows

Your application sends its prompt to Jnvoy. Jnvoy finds sensitive values and swaps each one for a token such as [PERSON_1]. Only the tokenised prompt moves on. When the reply comes back, Jnvoy swaps the tokens for the original values before the reply reaches you.

What is stored

Jnvoy keeps a record of each request so you can audit it. The record describes the request. It does not contain it.

Each customer can read only their own audit records and usage, using their own key. Operator keys can read the whole deployment, and the operator's compliance report routes need an operator key. Records are kept for the life of the deployment. If you need a different retention period, ask.

Jnvoy can also scan the model's reply for things that should not come back, such as keys, card numbers and prompt injection text. That check runs on the reply as it arrives, before real values are put back. It records counts only.

Who else sees redacted text

Jnvoy sends redacted text to other services to do its job. None of them receive the original values from Jnvoy.

  • The model provider you choose (for example Anthropic or OpenAI) receives the redacted prompt. Its own terms govern what it does with that text.
  • Anthropic, for the second check, receives the redacted text only when the check is switched on. It adds about a second per request. If that service is unavailable, Jnvoy carries on with the first-pass redaction. A customer can switch the check off for their own traffic, and a self-hosted deployment can run it on a model on its own machine instead.
  • Render hosts the Jnvoy service and its database. Request text is processed in the service's memory, and Jnvoy does not write original text to either. The security page lists every service we use.

What redaction does not promise

Detection combines pattern rules, a trained model for names and places, and the optional second check. Together they catch most of what we test for, and they can still miss a value or hide a harmless word.

  • Misses happen. Unusual formats, names with no surrounding context, and addresses written in free text are the likeliest to slip through.
  • Over-redaction happens too. A ten digit number can be read as an NHS number, and a brand name can be read as a person.
  • Our measurements are small. The labelled test set is in the repository, written by us, and you can run it yourself. Treat it as evidence, not proof.

For that reason Jnvoy's compliance report says no PII detected by Jnvoy was transmitted. It does not say none existed.

Sending text safely

  • Send text in the request body. Use POST /v1/scan. The old GET versions put your text in the web address, and web servers commonly record addresses in their logs. They have been removed and now answer with an error.
  • Your model provider key travels with each request. Send it in the x-provider-key header. It is used to make that one call, and is never stored, logged, cached or written to the audit log.
  • Keep your API key out of source code. Keys are checked in constant time, are never written to logs or responses, and can be rate limited.
  • Treat the second check as a choice. If your data cannot go to a second vendor in any form, set judge to off in your settings, or ask for it to stay off.
This page describes how the software behaves today. It is not a contract or legal advice. If your organisation needs a data processing agreement, ask before you send real data.
