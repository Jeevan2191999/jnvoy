# Threat model

Written on 4 November 2026 by the person who runs Jnvoy. It has not been reviewed by anyone outside the company, and Jnvoy has had no independent penetration test. Read it as a list of the ways Jnvoy can go wrong, what stops each one today, and what does not.

A test (`tests/test_threat_model.py`) fails if a row cites a test that does not exist, if a row says "partly" or "not done" without saying what is left, or if this page and the [security page](https://www.jnvoy.com/security) stop pointing at each other. It cannot check that the list of threats is complete. If you can think of one that is missing, please say so: see [SECURITY.md](SECURITY.md).

## What is being protected

| Asset | Where it lives | Why it matters |
|---|---|---|
| The original text of a request (prompts, files, tool results) | In the memory of the Jnvoy service while one request is processed. Never written to the database. It is also readable in transit by Cloudflare on the hosted service. | It holds the personal data and secrets Jnvoy exists to keep from the model provider. |
| A customer's Jnvoy key | Shown once. Stored as a SHA-256 hash. | It lets someone act as that customer. |
| A customer's own model-provider key | Sent in a header with each request. Used for that request. Never stored. | It spends the customer's money. |
| The audit record | Database. Counts of what was found, by type, with times and model names. | It describes a customer's traffic. |
| A customer's settings | Database. Regions, extra types, custom patterns, protected terms, allowlist, review step, reply scanning, injection check. | They decide what is redacted. A weakened setting lets data through. |
| The operator key | Environment variable on the host. | It can create customers and read every record. |
| Jnvoy's own provider keys | Environment variable on the host. | Never used for a customer's request. |

## Who and what could cause harm

1. An anonymous caller on the internet.
2. A customer who tries to read another customer's records or use their allowance.
3. Someone holding a stolen customer key.
4. Text that is hostile: a prompt, a file, a tool description, or a model reply.
5. A weak dependency or a bad update.
6. The operator, by mistake. There is one operator.
7. The hosting provider.

Not covered: attacks on a customer's own systems, on the model providers, or on a customer's staff.

## How a request travels (the trust boundaries)

Application, then Jnvoy over HTTPS (boundary 1: the key is checked here; on the hosted service the request also passes through Cloudflare, which can read it). Jnvoy finds and replaces sensitive values in memory (boundary 2: the original text exists only here). The redacted text goes to the model provider the customer chose, and to the optional second check where one is switched on (boundary 3: only redacted text crosses). The reply is scanned, real values are put back, and it returns to the application. The database receives counts only (boundary 4).

## What is not on this list

- Attacks on the model providers, and on the customer's network or staff.
- Legal and contract questions, which belong in the data processing agreement and the terms.
- Anything the operator has not thought of. If you find a gap, please report it.
